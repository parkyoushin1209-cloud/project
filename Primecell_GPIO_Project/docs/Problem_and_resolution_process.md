### Problem
- GPIODATA Alias 기능 처리
PL061에서 GPIODATA에 대한 액세스 동작은 다른 일반 레지스터와 구별되는 별도의 로직을 갖고 있었다. 이에 따라 처음 계획했던 Adapter, Predictor를 사용한 명시적 예측
방식을 이용할 경우 이 로직을 구현하기 어렵다는 점을 파악했다(이 로직을 구현하기 위해 기존 Predictor, Adapter를 확장한 커스터마이징 된 Predictor, Adapter 사용을
고려했으나 이 경우에도 masked address를 전달하기는 불가능했다.)

해결 과정 : 
명시적 예측이 불가능하다는 점을 고려해 스코어보드에서 암묵적 예측을 진행하도록 selected_bit라는 변수를 두었으며, 이 변수에 (PADDR >> 2)를 저장해 
마스크된 주소를 저장 후 스코어보드에서 직접 이 변수를 이용해 predict하는 방식을 이용했다.

- 인터럽트 로직 결과 미스 매치
스코어보드를 통해 참조 모델을 생성한 후 DUT에서 온 결과와 SCB에서 만들어진 결과를 비교하는 과정에서 많은 mismatch가 발생함을 알 수 있었다.
적은 양의 시퀀스만 사용해 테스트를 진행할 경우 별다른 문제가 없었으나 매우 많은 시퀀스를 실행할 경우 로그 도중에 mismatch가 발생했으며 EDA PlayGround라는 제한된
환경에서 출력 가능한 로그 수를 고려해 특정 범위의 타임에서의 로그만 출력할 필요가 있었다.

해결 과정 : 
특정 타임에서의 로그만 출력하기 위해 print_trigger라는 변수를 사용해 state == enable이 될 때마다 1씩 올리며 이 변수가 특정 값 이상일 때만 로그를 출력하도록 했다.
DUT와 TB에서의 mismatch 원인 중 가장 기억에 남았던 문제는 DUT에서는 매 상승 에지마다 결과를 수정하지만 TB에서는 트랜잭션이 스코어보드로 들어오는 시간에만 결과 예측 
로직을 수행해 발생한 문제였다. 이로 인해 intr_event의 값이 불일치 하는 문제를 발견했으며 이 문제를 찾아내기 위해 DUT와 Scoreboard의 동일 timestamp로그 비교, 
$display와 $strobe의 출력 비교를 통한 논블로킹 할당 확인, FSM 상태와 레지스터 업데이트 타이밍 확인, 인터럽트 이벤트 및 GPIOIC clear 조건 추적 등을 진행했다.
이 문제를 발견 후 해결하기 위해 DUT에서 매 클럭마다 업데이트 하도록 하지 않고 enable -> idle phase로 넘어가는 구간에서만 새로 업데이트 하도록 했다.

- 중복 선언 문제
컴파일 과정 중 특정 component, transaction 등이 중복으로 선언됐다 라는 문제가 발생했다.

헤결 과정 :
`include "uvm_macros.svh" 같은 공통적인 기능을 제외하고 대부분의 include는 testbench.sv에서만 진행한 후 다른 파일에서는 import pkg 방식을 사용해 문제를 해결할 수
있었다.
